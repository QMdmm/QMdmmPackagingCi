# AGENTS.md

Notes for whoever picks up a task here. `README.md` explains **why** the harness
is shaped the way it is and what each stage asserts; `release/README.md` does the
same for the release line. This file is what neither of them is: the map you need
**before** changing anything - what is where, what else moves when one thing
moves, what can be checked on a laptop, and what must not be touched.

This repository holds no product code. It packages and verifies
[QMdmm/QMdmm](https://github.com/QMdmm/QMdmm) on the distributions listed in
`release/lines.tsv`, and publishes the result to
<https://qmdmm.github.io/QMdmmPackagingCi>.

## Two workflows, one harness

| Workflow | Trigger | What it does |
|---|---|---|
| `packaging-smoke.yml` | daily cron + dispatch | Stages A/B/C against four container images and the macOS lines. **Nothing is signed and nothing is published** - deliberately, so the daily run needs no key at all. |
| `release.yml` | `workflow_dispatch` only | The same `ci/` scripts for stages A/B/C, then the `release/` layer on top: sign, assemble the site, push `gh-pages`, bump the tap, upload the `.dmg`. |
| `qt-version-matrix.yml` | daily cron + dispatch | Builds QMdmm's own sources against each supported Qt LTS. Shares nothing with the packaging harness. |

**`ci/` has two callers.** A change under `ci/` lands in the daily smoke run and
in a release at the same time; a change under `release/` only ever lands in a
release. When a change belongs to one of the two, say which in the file.

## What is where

| Path | What it is |
|---|---|
| `ci/` | The stage shell, shared by both workflows. `pack-<kind>.sh` / `runtime-<kind>.sh` / `dev-<kind>.sh` each own a whole stage for one kind (`deb` / `rpm` / `pac` / `apk` / `brew` / `macos`). `base-image-<kind>.sh` refreshes the base image and installs whatever package list its caller hands it. The platform-level checks - `runtime-verify-linux.sh`, `build-verify-linux.sh`, `run-verify-linux.sh`, and the `-macos.sh` pair - read `DIST_KIND` / `MACOS_FACE` for the two things that really differ per line. |
| `release/` | Everything only a release needs. `lines.tsv` is the line set; `sign-repo-*.sh` / `mkkeyring-*.sh` / `mkrepo-debian.sh` build the trust material; `consume-*.sh` are the consumer cells; `publish-brew.sh` / `publish-tap.sh` / `publish-macos.sh` are the three publishing endpoints; `assert-revision-tag.sh` and `assert-release-version.sh` are the guard's two questions. `lib-site.sh` / `lib-tools.sh` hold shared functions. |
| `packaging/` | The two recipes that do not go through CPack - `arch/PKGBUILD` (plus `.SRCINFO`, which is a **dotfile**: `ls` does not show it) and `alpine/APKBUILD` - each with a `NOTES.md` beside it explaining the shape. |
| `keys/` | Published OpenPGP material: the root's public half (`qmdmm-root.gpg` / `.asc`), one `<line>/qmdmm-packages.gpg` per line, and `fingerprints.txt`. |
| `site/` | The committed part of the published site - the `<line>-keyring/` stubs. Everything else on the site is generated by the publish job. |
| `consumer/` | Stage C's harness: a CMake project that builds QMdmm's own GUI / Bot / Server against the installed dev package. |
| `packaging/alpine/*.rsa.pub` | The Alpine line's two keys - the daily one and the release one. Not OpenPGP, so not under `keys/`. |

## Adding or moving a line

`release/lines.tsv` is the line set - one row per line and release, the only
place it is written down. (Its header row starts with a UTF-8 BOM; the data rows
do not.) A row needs, in the same change:

- the row itself (`line`, `fmt`, `consumer`, `version`, `container`, `expect`,
  `sfx_runtime`, `sfx_dev`);
- rows in `release.yml`'s matrices - `pack`, `verify-runtime` and `verify-dev`
  for every line, plus the two trust matrices: `trust-keyring` for the OpenPGP
  lines and `trust-consume` for all of them;
- a key story, if the line is published (see the two rules below).

Two things about the release job graph are asymmetric on purpose and easy to
"fix" wrongly:

- **`publish` waits on the Alpine rows' stages B and C directly** -
  `needs: [sign, pack-apk, verify-runtime-apk, verify-dev-apk]`. Every other
  line's verify stages are collected by `sign`, so `needs: [sign]` carries them;
  the Alpine line has **no signing stage** (abuild signs inside stage A and
  cannot be told not to), so nothing else would carry its verify stages, and a
  red stage B or C there would publish anyway.
- **`keys/fingerprints.txt` has no Alpine row, and that is a declaration rather
  than an omission.** Alpine is not an OpenPGP line, and
  `release/check-fingerprints.sh` lists it as explicitly exempt instead of
  silently skipping it.

Stage A asserts the package names it expects, and the expectation is written in
the line's `expect` field rather than derived from a prefix - Alpine is why: on
that line `qmdmm` is a prefix of every other name, so a suffix match would prove
nothing.

## Changing a version

Nothing in the release path invents a version, and
`release/assert-release-version.sh` - the guard's second question - fails the run
when the pieces disagree. The pieces:

1. the tag name (`refs/tags/` stripped, and a leading `v`);
2. `project(... VERSION ...)` in **the tag's tree** of the QMdmm repository -
   which is also where deb and rpm get their version from, through CPack;
3. `packaging/arch/PKGBUILD` -> `pkgver`;
4. `packaging/arch/.SRCINFO` -> `pkgver` (the dotfile above);
5. `packaging/alpine/APKBUILD` -> `pkgver`.

brew and macOS read the version out of the source tree instead, which is why
neither appears in that list.

The two recipes also pin a checksum of `git archive` of that tag - `PKGBUILD`'s
`sha256sums` over `qmdmm-6-<ver>.tar.gz`, `APKBUILD`'s `sha512sums` over
`qmdmm-<ver>.tar.gz`. Both change whenever the tag moves and neither is
derivable; recompute them (`git archive --format=tar.gz --prefix=... -o ... <tag>`
then `shasum -a 256` / `-a 512`) rather than trusting a previous value.

The version assertion lives in the release's guard and **not** in `ci/`, on
purpose: the daily smoke run packages `main`, whose version climbs on its own
schedule, and a check there would turn every version bump into a red run.

## Checking a change before you push it

Rules that make a laptop preflight worth anything:

- `bash -n` every script you touched. There is no `shellcheck` here.
- **Slice the step you are changing out of the workflow** and run that, rather
  than re-typing what you think it says. `release.yml` is the source of truth; a
  copy of it is not.

  ```bash
  python3 - <<'PY'
  import yaml
  d = yaml.safe_load(open('.github/workflows/release.yml'))
  for s in d['jobs']['publish']['steps']:
      if s.get('name') == 'Assemble the site':
          open('/tmp/assemble-site.sh', 'w').write(s['run'])
  PY
  ```

- **Feed the preflight real artifacts, not invented ones.** Download them from a
  run (`gh run download <id> -n <artifact> -D <dir>`) and use those bytes. Twice
  now a preflight passed against a fixture whose *name* was assumed - it created
  `pack-apk-3.21` while the workflow uploads `pack-alpine-3.21` - and the real
  run failed on exactly that. The artifact name is an interface: `pack-<line>-<version>`.
- **Run under the engine the step will run under.** This laptop's tools are BSD
  and the runners' are GNU, and the difference is not cosmetic: `grep -qE '...\t...'`
  finds a tab under GNU grep and a stray escape under BSD, and `sha256sum` does
  not exist here at all. Shim the names you need -
  `printf '#!/bin/sh\nexec shasum -a 256 "$@"\n' > /tmp/gnu-tools/sha256sum` (same
  for `sha512sum`), `chmod +x` - then `PATH=/tmp/gnu-tools:$PATH bash ...`.
- `release/assert-release-version.sh` runs against the real remote from here:
  `REVISION=<tag> bash release/assert-release-version.sh`.
- Anything that needs a container or a macOS runner - stages A/B/C, `otool`,
  `hdiutil` - cannot be checked here. Say so in the change, and let a run be the
  check.

## Running a release end to end

```bash
gh workflow run release.yml -f qmdmm_ref=<tag>
```

**Dispatching is publishing.** The run replaces the whole `gh-pages` tree,
uploads the `.dmg` to the QMdmm release and pushes the tap. There is no dry-run
mode, which is what the package line's own branch is for:

- QMdmm's `0.0.z` branch is the release-testing line; `main` is the product. Each
  carries its own `project(... VERSION ...)` (0.0.3 against 0.1.0 while this was
  written), so a test release is a tag on `0.0.z` and a version bump there never
  reaches a product version.
- Keep two working copies of the QMdmm repository - one checked out on `main`,
  one on `0.0.z` - rather than moving one clone between branches. A clone left
  sitting on `0.0.z` makes every later `git log`, tag listing and build in it run
  against the wrong tree, and nothing here reports that.

Two publishing behaviours are deliberate and should not be "improved":

- **`.dmg` uploads are additive.** A second dispatch at the same version reports
  the existing asset, does nothing and exits 0 - the image is not reproducible,
  so re-uploading would replace bytes nobody asked to replace. To really replace
  one, delete the asset on the release first.
- **A staged line is removed before it is copied** (`rm -rf _site/<line>/<ver>`),
  and the `gh-pages` tree is cleared before `_site` is laid down. So the site
  never accumulates old versions, and a file put there by hand does not survive
  the next release. `publish-brew.sh` writes into `$SITE` and does not push; the
  publish job's own `gh-pages` step carries its output up.

## What must not be touched

- **`keys/` is source, not scratch.** `fingerprints.txt` is what the publish job
  asserts the served key files against, so adding a line's key means adding its
  row there in the same change. The root's private half is in no environment, in
  no secret and in no file here; `keys/qmdmm-root.gpg` is the public half only.
- **Never put a private key anywhere but a secret.** The seven OpenPGP lines read
  `secrets.SIGNING_KEY` from an environment of their own; the Alpine daily key
  comes from the repository-level `PACKAGER_PRIVKEY`; the Alpine release key from
  the `alpine` environment's `SIGNING_KEY` - the same secret name as the other
  lines, so that the declared environment is what picks the line. The daily
  workflow declares no environment and therefore cannot read the release key.
- **On Alpine, the key's file name is the identity.** `PACKAGER_KEY` and
  `packaging/alpine/<name>.rsa.pub` have to agree, because apk resolves
  `.SIGN.RSA.<basename>` member names in `/etc/apk/keys`. There is no revocation:
  rotating means a new name plus asking every consumer to replace the file.
- **Do not hand-edit `site/`** beyond what is committed there. The publish job
  replaces that branch's whole tree.

## What runs on its own

`packaging-smoke.yml` and `qt-version-matrix.yml` carry cron schedules: they run
daily whether or not anyone asks, so a red run there sits until someone looks.
`release.yml` is the other kind - `workflow_dispatch`-only, with no time-driven
work of its own - so sitting idle is its normal state, and the person who
dispatched a run is the one watching it.
